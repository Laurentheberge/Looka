# PROJECT FOUNDATION SYSTEM

## STEP 5: BUILD
### Controlled Implementation and Feature Development

Read the project documentation before implementing anything.

Build the application according to the established requirements, architecture and design
system.

## BUILD RULES

- Check project health before new work.
- Create a build roadmap.
- Work in small logical units.
- Follow dependency order.
- Build foundations before dependent features.
- Reuse existing components.
- Follow the design system.
- Use the selected icon library.
- Do not use emojis as UI icons.
- Do not create fake functionality unless explicitly requested.
- Handle loading, empty and error states.
- Make interfaces responsive.
- Validate important forms.
- Enforce permissions.
- Test each task.
- Check for regressions.
- Update task status.
- Update documentation when implementation changes it.
- Keep UI copy natural.
- Avoid unnecessary emojis, decorative symbols, em dashes, en dashes and AI-style filler.
- Do not claim something is verified unless it was tested.

## FEATURE WORKFLOW

```text
UNDERSTAND
↓
CHECK EXISTING CODE
↓
PLAN
↓
IMPLEMENT
↓
TYPE CHECK
↓
LINT
↓
TEST
↓
VERIFY
↓
DOCUMENT
↓
MARK DONE
```

## DEFINITION OF DONE

A task is complete when applicable:

- Requirements are understood.
- Implementation is complete.
- Existing code was reused where appropriate.
- Design system is followed.
- Responsive behavior is checked.
- Validation is handled.
- Loading state is handled.
- Empty state is handled.
- Error state is handled.
- Permissions are checked.
- Tests/checks are run.
- No new errors are introduced.
- Documentation is updated.
- `docs/TASKS.md` is updated.

## MVP REPORT

When the planned MVP is complete, create:

`docs/MVP_REPORT.md`

Include:

- Project status
- Completed features
- Remaining features
- Known issues
- Testing
- Unverified items
- Technical debt
- Future features
- Deployment status

Do not declare the MVP complete if critical work remains.
